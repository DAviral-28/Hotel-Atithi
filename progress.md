# Hotel Booking Project - Progress & Architecture Tracker

## 1. Project Overview
Full-stack serverless hotel booking system for **Hotel Atithi**, a 32-room hotel situated on Station Road, Gular Naka, Banda, Uttar Pradesh - 210001 (Near Banda Railway Station). Designed for zero recurring charges on the AWS Free Tier and deploying to region `ap-south-1` (Mumbai). Features an Oyo-style atomic concurrency reservation engine with distributed lock handling, hold expiration, booking confirmation, checkout extension capabilities, zero-fee payments (Pay at Hotel or UPI QR), self-service cancellation with a 24-hour free-cancellation policy, a GST-compliant tax invoice, an RFC-compliant security layer (RFC 7515 JWS token signing & RFC 7516 JWE guest PII encryption, HMAC-SHA256 blind indexing, masked phone lookup, in-memory rate limiting, strict input validation, CORS allow-list and security headers), a zero-cost front-desk staff console (PIN login, check-in / check-out, walk-ins, UPI reconciliation, room maintenance blocking), free WhatsApp / optional SES confirmations, and a customer-facing Single Page Application (SPA) built with React 18, Vite, TypeScript, and Tailwind CSS, styled in a warm hospitality theme and hosted on AWS S3 + CloudFront CDN.

## 2. Completed Architecture Decisions

| Decision Area | Choice | Justification |
| :--- | :--- | :--- |
| **Property Identity** | Hotel Atithi, Banda | Real property identity on Station Road, Gular Naka, Banda, UP (Near Railway Station). Contact: `+91 94523 14397`. Standard check-in / check-out: `12:00 PM`. |
| **Customer Experience** | Pure Hospitality Focus | Elimination of internal cloud/developer jargon (e.g., "RFC 7515/7516", "DynamoDB Free Tier", "ap-south-1 Mumbai") in favor of genuine guest highlights: Free Wi-Fi, 24/7 Front Desk, 100% Power Backup, Room Service, and Instant 10-Minute Hold Locking. |
| **Resilience & Offline Fallback** | Static room list only — never fake bookings | In addition to the Vite proxy (`/api` -> `http://localhost:8080`), the frontend keeps an embedded copy of the 32-room catalogue (static tariffs) for display. **All booking behaviour (availability, hold, confirm, pay, extend, cancel) is server-only**: if the API is down or offline the UI shows an error banner with "Try again" (`ApiError` / `ErrorBanner`). The offline hold/confirm/extend/lookup simulation was removed in Milestone 11. |
| **Payments (zero cost)** | Pay at Hotel or UPI QR + UTR | No payment gateway, so no fees. `PaymentMethod` = `PAY_AT_HOTEL`, `UPI_QR`; `PaymentStatus` = `PENDING`, `PAID_ONLINE`, `DUE_AT_CHECKIN`. UPI uses an NPCI `upi://pay?pa=&pn=&am=&tn=Booking-<id>&cu=INR` link rendered as a QR by an in-repo encoder (`utils/qr.ts`); the guest enters the 12-digit UTR. The UTR is self-declared — each UTR can be used once (DynamoDB claim item) and staff reconcile it against the UPI statement. |
| **Cancellation policy** | Free until 24h before check-in 12:00 PM IST | Later cancellations need explicit acknowledgement and are flagged `lateCancellation`; refused once check-in time is reached. Refunds are processed manually by the hotel. |
| **Booking management auth** | Signed "manage" token (JWS, `purpose=manage`) | Issued on confirmation or after phone verification (`POST /{id}/access`); required for cancel, extend and pay-balance. Expires 30 days after check-out. A hold token can never be used to manage a booking. |
| **GST invoice** | SAC 996311, CGST 2.5% + SGST 2.5% | Itemised tariff, extra-guest charges and taxes. Legal name / GSTIN come from `VITE_HOTEL_LEGAL_NAME` / `VITE_HOTEL_GSTIN` (not hard-coded). |
| **AWS Region** | `ap-south-1` (Mumbai) | Low-latency domestic access for Indian hotel operations and GST compliance. |
| **Hosting Strategy** | Zero-Cost Tier (Serverless) | Strict zero recurring costs. No ECS Fargate clusters, NAT gateways, or always-on EC2 instances. |
| **Frontend Architecture** | Single Page Application (SPA) | Vite + React 18 + TypeScript + Tailwind CSS with warm hospitality aesthetics (`stone-50` neutrals, `amber-600` accents). Static production bundle in `/frontend/dist`. |
| **Frontend Static Hosting** | Amazon S3 + CloudFront CDN | AWS Free Tier (S3: 5 GB storage, 20k GET; CloudFront: 1 TB transfer/month forever free). $0 recurring hosting cost. |
| **CloudFront Security** | Origin Access Control (OAC) | S3 bucket blocks all public access; CloudFront delivers assets using SigV4 signed requests. |
| **SPA Client Routing** | CloudFront Custom Error Responses | Maps 403 and 404 HTTP errors to `/index.html` with status 200 for seamless client-side routing. |
| **Database** | Amazon DynamoDB | Single-table design. Provisioned capacity at 5 RCU / 5 WCU with auto-scaling safety to stay perpetually within the AWS 25 RCU/WCU Free Tier limit. |
| **PII Encryption at Rest** | RFC 7516 JWE (AES-256-GCM / `dir`) | Direct key authenticated encryption for guest phone, email, and name. Ciphertexts are authenticated with GCM tags; any bit-level tampering in DynamoDB causes immediate decryption failure. |
| **Searchable Blind Indexing** | HMAC-SHA256 with a secret pepper *(M12)* | The canonical 10-digit guest phone is hashed with HMAC-SHA256 keyed by `HOTEL_HMAC_PEPPER` (or a key derived from `HOTEL_ENCRYPTION_KEY_256`) for `GSI1PK` (`GUEST#<hmac>`). Unlike the earlier unsalted SHA-256, the ~4x10^9 valid mobile numbers cannot be brute-forced from the index without the pepper. Rows written before M12 (plain SHA-256) are found through a fallback query and re-keyed lazily. |
| **Phone canonicalisation** *(M12)* | `PhoneNormalizer` (Java + TypeScript) | Strips spaces, hyphens, dots, parentheses, `+91` / `91` and leading zeros; canonical form `^[6-9]\d{9}$`. Invalid input is a 400 before any DynamoDB call or hashing. |
| **Phone privacy** *(M12)* | Masked lookup + two-factor access | A phone number alone (`GET /lookup?phone=`) returns only masked summaries (partial booking ID, status, dates, room category, masked name). Booking ID + last 4 digits (`POST /lookup`) gives a masked view; Booking ID + FULL phone (`POST /{id}/access`) is the only way to a manage token. `GET /{id}` no longer returns tokens or unmasked PII. |
| **Abuse protection** *(M12)* | In-memory sliding-window limiter | 3 holds / IP / 10 min; 5 lookup + access attempts / IP / min; HTTP 429 + `Retry-After`. Zero cost (JVM memory, per Lambda instance); API Gateway stage throttling is the global backstop. |
| **CORS & headers** *(M12)* | Exact-origin allow-list + security headers | CloudFront domain + local dev origins `http://localhost:5173` / `http://localhost:3000` (never `*`) on API Gateway and Spring; `X-Content-Type-Options`, `X-Frame-Options`, `Strict-Transport-Security` on every API response, on API Gateway error responses and on the CloudFront-served site. |
| **Staff authentication** *(M13)* | Shared PIN -> signed session token | `HOTEL_STAFF_PIN` (default `1439`) is checked in constant time; a correct PIN returns an RFC 7515 JWS (HS256, `purpose=staff`, key derived from the signing secret with a domain label, PIN fingerprint claim) valid 8-12 h (default 10), sent as `X-Staff-Token` / `Authorization: Bearer`. Guest hold / manage tokens are rejected on staff routes; changing the PIN signs everyone out. Login is rate-limited (5 / IP / 5 min). No paid auth service. |
| **Front-desk console** *(M13)* | `/staff` route in the same SPA | Same S3 + CloudFront site; `main.tsx` renders `StaffConsole` for `/staff` (CloudFront already maps unknown paths to `index.html`). PIN lock, stats, operations, room grid, block / unblock, walk-in, UPI verification. |
| **Room maintenance** *(M13)* | `InventoryStatus.MAINTENANCE` rows | Blocking writes MAINTENANCE inventory rows with the same conditional lock as a hold, so the public cannot hold / book / see the room and a block can never overwrite a booked night. Unblock deletes only MAINTENANCE rows. |
| **UPI reconciliation queue** *(M13)* | `RECON#PENDING` marker rows | Written in the same transaction as a UPI confirm / pay, deleted when staff verify; the dashboard reads it with one Query on the partition key (no scan, no new GSI). |
| **Guest notifications** *(M13)* | WhatsApp deep link + optional SES | `https://wa.me/91<phone>?text=` button on the slip (no account, no fees). `NotificationService` sends an HTML e-mail through AWS SES v2 only when `AWS_SES_SENDER_EMAIL` is set; otherwise it logs; every failure is swallowed so a booking never fails. |
| **Tamper-Proof Tokens** | RFC 7515 JWS (HMAC-SHA256 / `HS256`) | Each booking hold issues a cryptographically signed compact JWS token binding `bookingId`, `roomNumber`, `checkInDate`, `checkOutDate`, `totalAmount`, and expiration `exp`. Confirmations require this token and verify its signature against stored records to stop price/date tampering. |
| **Concurrency Control** | DynamoDB `TransactWriteItems` | Atomic ACID multi-item transactions across stay dates with conditional expressions (`attribute_not_exists(PK) OR #status = 'AVAILABLE' OR (#status = 'HOLD' AND #lockExpiresAt < :now)`). Prevents double-booking. |
| **Hold Lifecycle** | 10-Minute Ephemeral Lock | Rooms held temporarily for 600 seconds. If confirmation isn't completed in time, the hold automatically expires and subsequent requests overwrite it without requiring background reaper sweeps. |
| **Backend Runtime** | Java 21 on AWS Lambda | Long Term Support (LTS) managed runtime with modern language features (Records, Pattern Matching, Virtual Threads). |
| **Application Framework**| Spring Boot 3.3.4 + AWS Serverless Java Container | `aws-serverless-java-container-springboot3` proxies API Gateway requests into Spring controllers with sub-millisecond execution overhead. |
| **API Layer** | Amazon API Gateway (REST API) | Edge-optimized REST API with regional deployment, CORS restricted to the CloudFront site + local dev origins (M12), security headers on gateway error responses, and proxy routing to Lambda. |
| **Infrastructure as Code**| AWS CDK v2 (TypeScript) | Strongly typed, reproducible cloud infrastructure targeting `ap-south-1`. |

## 4. DynamoDB Schema & Security Indexing (`HotelBookings`)

### Table Attributes & Indices
- **Table Name**: `HotelBookings`
- **Partition Key**: `PK` (String)
- **Sort Key**: `SK` (String)
- **Time-to-Live (TTL)**: `ttl` (Epoch timestamp in seconds for automatic data lifecycle management)
- **Global Secondary Index (GSI1)**:
  - **Index Name**: `GSI1`
  - **Partition Key**: `GSI1PK` (String: `GUEST#<hmac-sha256(pepper, canonical phone)>` - **Blind Indexed**; rows written before M12 hold `GUEST#<sha256(phone)>` and are re-keyed lazily)
  - **Sort Key**: `GSI1SK` (String: `BOOKING#<CheckInDate>`)
  - **Projection**: `ALL`
  - **Capacity**: 5 RCU / 5 WCU (Provisioned Free Tier)

| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| **Room Definition** | `ROOM#<RoomNo>` | `METADATA` | `ROOM_TYPE#<Type>` | `ROOM#<RoomNo>` | `type`, `bedType`, `baseRate`, `extraPersonRate`, `floor`, `baseOccupancy`, `maxOccupancy` | Static catalog lookup. |

## 6. Security & Concurrency Mechanisms Implemented

1. **RFC 7516 (JWE) Authenticated Encryption at Rest**:
   - Guest Personally Identifiable Information (`guestName`, `guestPhone`, `guestEmail`) is encrypted via direct AES-256-GCM (`A256GCM` / `dir`).
   - Ciphertexts include Galois/Counter Mode authentication tags, preventing bit-flipping attacks.
2. **Deterministic Blind Indexing (HMAC, M12)**:
   - The canonical 10-digit phone is hashed with HMAC-SHA256 keyed by a secret pepper before writing to `GSI1PK` (`GUEST#<hmac>`). Every write of a booking re-derives it, so legacy SHA-256 rows are upgraded as they are touched, and lookups also query the legacy keys (`hotel.security.legacy-index-fallback`, default on) and re-key what they find.
   - Enables fast guest booking lookups without exposing plain phone numbers in DynamoDB secondary indices, and without letting anyone who reads the index recompute the hash for every possible number.
3. **RFC 7515 (JWS) Tamper-Proof Booking Tokens**:
   - Emits a signed compact JWS token (HS256) upon successful room hold.
   - Token binds: `bookingId`, `roomNumber`, `checkInDate`, `checkOutDate`, `totalAmount`, and `exp`.
   - `confirmBooking` requires this token (via header `X-Booking-Token` or JSON body) and verifies signature integrity and claim equivalence against stored DynamoDB state to prevent client-side price or date alteration.
4. **Atomic Room Locking (`TransactWriteItems`)**:
   - Every reservation stay date is locked atomically in a single multi-item ACID transaction.
   - If any single date fails the condition `attribute_not_exists(PK) OR #status = 'AVAILABLE' OR (#status = 'HOLD' AND #lockExpiresAt < :now)`, the entire transaction aborts without partial writes.
   - HTTP 409 Conflict is returned containing the exact conflicting dates.
5. **Deterministic Hold Expiration Without Sweeper Workers**:
   - The lock expiration timestamp (`lockExpiresAt = now + 600s`) is part of the conditional check expression.
   - Expired holds are overwritten automatically by subsequent incoming requests, removing the need for a recurring scheduled cleaner task or Lambda worker.
6. **Frontend Zero-Cost SPA Architecture**:
   - Client build outputs static assets to `/frontend/dist`.
   - Hosted on S3 with CloudFront CDN under AWS Free Tier.
   - Origin Access Control (OAC) prevents direct S3 public access.
   - Custom CloudFront error responses route 403 and 404 requests to `/index.html` (HTTP 200).
7. **No Fake Bookings (Milestone 11)**:
   - The frontend never simulates a hold, confirmation, extension or lookup. Server failures surface as an `ApiError` with an actionable banner and retry; only the static room list is kept locally for display.
8. **Manage Token (Milestone 11)**:
   - `BookingTokenService.generateManageToken` / `verifyManageToken`: JWS HS256 with `purpose=manage`, `bookingId`, exp = check-out + 30 days. Cancel, extend and pay-balance require it (`X-Booking-Token`); failures return 403. Obtained at confirmation, on an idempotent confirm replay (only with the original hold token, expiry ignored) or via `POST /{id}/access` with the guest's phone.
9. **Payments & Cancellation Integrity (Milestone 11)**:
   - UTR uniqueness via claim items; optimistic `amountPaid` check on pay-balance; cancel is a single transaction (booking → `CANCELLED`, inventory rows deleted with `bookingId` condition) and is idempotent.
10. **Phone Privacy & Two-Factor Lookup (Milestone 12)**:
   - A phone number is not a secret. `GET /api/bookings/lookup?phone=` returns only masked `BookingSummaryResponse` items; the type has no name / phone / e-mail / token / full-ID / amount fields, so it cannot leak them. `POST /api/bookings/lookup` (Booking ID + last 4 digits or full phone) returns a masked `VerifiedBookingSummary`; wrong ID, wrong phone and unknown booking give the same 404 message (no probing). Only `POST /{id}/access` (Booking ID + FULL phone) yields a manage token. `GET /{id}` returns masked PII and never a hold / manage token or UTR.
11. **Abuse Protection (Milestone 12)**:
   - `SlidingWindowRateLimiter` per client IP (`request.getRemoteAddr()`; `X-Forwarded-For` is deliberately ignored because clients can forge it). Hold: 3 / 10 min. Lookup + access (shared bucket): 5 / min. Over the limit: 429, `Retry-After`, JSON `{error: TOO_MANY_REQUESTS, message, retryAfterSeconds}`. Settings in `hotel.security.rate-limit.*`. State is per Lambda instance (documented trade-off); API Gateway stage throttling (50 rps / 100 burst) is the global backstop.
12. **Input Validation (Milestone 12)**:
   - Jakarta Bean Validation on `HoldBookingRequest`, `AccessBookingRequest`, `ConfirmBookingRequest`, `PayBalanceRequest`, `LookupBookingRequest`; compact constructors strip markup from names and canonicalise phones first. UTR: exactly 12 letters/digits, stored upper-case, unique via the claim item.
13. **CORS & Security Headers (Milestone 12)**:
   - Exact-origin allow-list (`HOTEL_ALLOWED_ORIGINS` = CloudFront URL + `http://localhost:5173` and `http://localhost:3000` (the port in `vite.config.ts`), plus optional `HOTEL_EXTRA_ALLOWED_ORIGINS` at deploy time); `*` is rejected. Servlet filters add `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Strict-Transport-Security: max-age=31536000; includeSubDomains` (plus `Referrer-Policy: no-referrer`, `Cache-Control: no-store`) to every API response; API Gateway gateway-error responses and the CloudFront site carry the same headers.

14. **Staff Authentication & Role Separation (Milestone 13)**:
   - One role: front-desk staff. `StaffAuthService.login` compares SHA-256 digests of the supplied and configured PIN with `MessageDigest.isEqual` (constant time, independent of PIN length). The token is an HS256 JWS with `purpose=staff`, an `exp` of 8-12 h and a `pinFp` claim (HMAC of the PIN under the token key); `requireStaff` checks signature, purpose, expiry and `pinFp`. The key is `HMAC(signingSecret, "hotel-staff-session-token/v1")`, so it is not the booking-token key. Every `/api/staff/**` endpoint except `/login` calls `requireStaff` first (401 otherwise). Guest tokens (hold / manage) fail the purpose check on staff routes; a staff token has no `bookingId`, so it fails every guest check. `POST /api/staff/login` is limited to 5 attempts / IP / 5 min (429 + `Retry-After`). Staff responses show full guest name / phone / e-mail (staff are authenticated) but never a token.
   - Limits (documented): a 4-digit default PIN is guessable given time; set `HOTEL_STAFF_PIN` to 6+ digits. Rate-limit state is per Lambda instance. It is a shared PIN, so there is no per-person audit trail.
15. **Front-desk state machine (Milestone 13)**:
   - `CONFIRMED -> CHECKED_IN` (not before the check-in date, not after check-out; idempotent) and `CHECKED_IN -> CHECKED_OUT` (idempotent; a checkout before the booked check-out date deletes only the booking's own unused nights, so the room is sellable again at once; an unpaid balance does not block checkout, the response shows it). All writes are conditional on the current status. Extend and pay-balance also accept `CHECKED_IN`; cancel stays `CONFIRMED` only.
   - Payment reconciliation (`verify-payment`): with a balance due the desk collects the whole balance (or `amountCollected`, never more than the balance, never negative) -> `PAID_AT_DESK`; with nothing due, a UPI payment is marked verified. It writes `paymentVerifiedAt`, guarded by an optimistic `amountPaid` check, and removes the reconciliation marker.
   - Maintenance: block covers inclusive nights (max 90, not in the past); overlap with a booking / live hold is a 409 listing the dates and nothing is written; unblock deletes only MAINTENANCE nights in the range (default: today onwards).
   - Walk-in: booking is created as `CHECKED_IN` (arriving today, default) or `CONFIRMED` in one transaction with its CONFIRMED nights (same lock rule as a hold); no hold, token or public rate limit; same tariff / GST maths, phone canonicalisation and name sanitising as the public flow.
16. **Guest notifications (Milestone 13)**:
   - WhatsApp: a pure link builder (`https://wa.me/91<canonical phone>?text=<encodeURIComponent(message)>`), message = hotel name, booking ID, room number, check-in / check-out dates with 12:00 PM IST, payment status (`Paid Online`, `Paid at the front desk` or `₹X Due at Check-in`), reception phone, address / landmark and a maps search link. No link is offered when the phone is masked or invalid.
   - E-mail: `NotificationService` (HTML + text, all guest text HTML-escaped) -> `EmailGateway` -> `SesEmailGateway` (SES v2). Off unless `AWS_SES_SENDER_EMAIL` is set; no valid guest e-mail, an unconfigured sender, a repeat for the same booking (idempotent confirm replay) or any gateway exception all end in a log line, never in a failed booking.
